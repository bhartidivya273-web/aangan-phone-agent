### Design decisions
- **Business rules at runtime (FR18).** `src/lib/rules.ts` reads `context/*.md` on every call (no cache). I added **`context/outcomes.md`**: the outcome table, proposed rules and flag vocabulary copied from the PRD, so Nikhil can edit them without code. `services.md`, `qualified.md`, `pricing.md` are loaded as-is. The approved price line is extracted from `pricing.md` at runtime (the em dash in that file is authoritative; the PRD copy uses a hyphen).
- **`pricing.md` goes to the classifier, never to the agent (Stage 2).** The classifier needs it to judge "volunteered budget far below scope" (T10). It is told never to copy numbers. The conversational agent will get only the approved line.
- **Classifier output.** Strict JSON validated with zod (`src/lib/schema.ts`): `outcome`, `reason`, `extracted`, `flags`, `pricing_asked` as specified, plus `underlying_outcome` (only for `repeat_caller`: what the call would otherwise have been, so a repeat qualified caller still gets one updated note) and `extracted.timeline_weeks_from_call` / `message_for_team`. One repair retry on invalid JSON; then the call is logged as `classification_status=failed` and Nikhil is alerted (calls are never lost).
- **Plain JSON + zod instead of the API's structured-output mode.** Keeps the code model-agnostic (MODEL_CLASSIFIER can be any model) and gives the same guarantee through validation + retry. Revisit if the retry rate is non-trivial.
- **No sampling params, no forced tool use.** Current models reject them. `EFFORT_CLASSIFIER` (default `low`) controls reasoning depth; empty omits the parameter for models that do not accept it.
- **Code guards after the model answers** (always recorded in `calls.guards`, never silent): add `pricing_asked` / `after_hours` / `repeat_caller` flags from facts the code knows; downgrade `qualified` -> `timeline_too_short` when extracted weeks < the hard minimum; add `timeline_tight` in the tight band. Date arithmetic is deliberately code's job.
- **Server-side refusal fallbacks (`fallbacks` param) are not enabled.** A refusal throws, goes through the failure path above and alerts Nikhil. Tell me if you want fallbacks on.
- **Repeat callers.** Merge key is the caller ID, normalised (digits, India prefix stripped). New non-null values overwrite, null never erases. A repeat qualified call sends ONE note: `UPDATED LEAD`, threaded as a reply to the earlier note, and the earlier note's unclaimed-alert is cleared (superseded). If the earlier note was already claimed, the update raises no new unclaimed alert. Where the transcript itself holds two calls (T17), the classifier sees one call.
- **Handoffs** go out as plain text (no Markdown parse mode: caller-supplied names need no escaping). Telegram failures retry 3x with backoff, then are stored as `status=failed` and retried by the cron route; the call log is always written first-class. The note's "Call summary" link points at `/dashboard/calls/<id>`, which arrives in Stage 3.
- **Claim by reply.** A designer replies to the note with a phrase like "taking it" / "mine" / "on it" (`TELEGRAM_CLAIM_PATTERN` overrides). First claim wins atomically; later claims get "Already claimed by X". The webhook checks `X-Telegram-Bot-Api-Secret-Token`.
- **Unclaimed alert.** `GET /api/cron/unclaimed` (Bearer `CRON_SECRET`) alerts Nikhil once per unclaimed note past `due_at`. Vercel Hobby only allows daily crons, so run this every few minutes from Vercel Pro cron, GitHub Actions or an external pinger. I did not add `vercel.json` cron yet; see README (Stage 3).
- **Call log schema** (`supabase/migrations/0001_init.sql`): `calls`, `leads`, `handoffs`, `costs`. A trigger blocks deleting calls with outcome `not_a_fit`, `escalate` or `timeline_too_short` (declined and escalated, FR12). RLS is on with no policies: all access is server-side with the service role key. **The migration has not been run against a real database yet.**
- **Costs.** One `costs` row per component (classifier tokens, agent tokens, voice minutes, telephony). Unit prices are env-configurable and default to 0, so amounts are 0 until you set `PRICE_*`. I did not hard-code model prices or an FX rate. Cache-read tokens are costed at the input rate (slight over-estimate).
- **Transcript hygiene in replay.** The only edit to a test transcript is stripping the `- ESCALATE` label from T09's header, because it leaks the expected answer. Staff `Note:` lines are left in (they are part of the real data) and the prompt tells the model they are evidence only.
- **Price-leak filter** (`src/lib/priceFilter.ts`) is intentionally over-eager: currency symbols/words, lakh/crore, "k" amounts, per-sq-ft forms, numeric ranges (allowing time/room units such as "3-4 weeks"), multiples ("3x", "three times"), "it'll cost" style phrases. In Stage 2 a flagged agent reply is replaced by the approved line. Known false-positive risk: reading a phone number back with a hyphen could trip the range rule.

## Stage 2 - the conversational agent (2026-10-09)

### What was built
- `src/lib/agent.ts`: `agentTurn(state, callerUtterance)` returns `{ say, state, closed }`. Pass `null` for the first turn to get the greeting. State is plain JSON (history, mode, price-ask count, signals, guards, token usage) so a stateless webhook can store it between turns (Stage 3).
- `context/agent.md` (new, editable by Nikhil): the greeting (which carries the AI disclosure), the complaint-callback wording, fixed fallback lines and the style rules. Loaded at runtime like the other context files.
- `src/lib/promiseFilter.ts`: no-promise filter (clock times, "within X", "shortly", confirmed/booked slots) and one-question enforcement.
- `scripts/simulate.ts` (`npm run simulate`): plays the test callers against `agentTurn`, then runs `classifyCall` and the full pipeline on an in-memory store with a console notifier (nothing is sent to Telegram).

### Design decisions
- **Code decides the wording that matters; the model decides the conversation.** The greeting/disclosure, the price response, and the complaint callback line (the only sentence that names a time) are all composed by code from `context/agent.md` and the approved line in `pricing.md`. The model reports intent flags (`price_asked`, `intent`, `close`) as JSON and never writes those sentences.
- **Price handling.** 1st ask: exactly the approved line. 2nd ask: the booking-offer sentence (the last sentence of the approved line, taken verbatim) followed by the agent's next question ("offers the booking once more and moves on"). 3rd+ asks: the agent just moves on with its next question. Open interpretation: the spec does not say whether the second-ask reply should also carry a question; I let it. Every spoken line then goes through the price filter; a leak is replaced by the approved line and logged in `state.guards`.
- **The agent never sees `pricing.md`** (the internal per-sq-ft guide). Caveat: `qualified.md` itself contains one rupee example ("1-1.5 lakh for a full flat redesign"), so the agent does see that one figure through the rubric. The output filter is the protection; if you want it gone, reword that line in `qualified.md` (Nikhil's file, so I did not touch it).
- **No promised times or slots.** Model replies are scanned; offending sentences are dropped and the rest kept; if nothing is left, a fixed fallback from `agent.md` is spoken. On a complaint close, the model's own callback sentences are stripped and the single code-composed callback line is added (15 minutes in office hours, 10:30am next office morning otherwise; both proposed targets from the spec).
- **One question at a time** is enforced in code (reply is cut after the first question mark) as well as in the prompt.
- **Human requested / not understood (FR22):** the model flags it, the state switches to take-message mode (name and what it is about, then "someone from the team will call you back", no time), and a `human_requested` / `not_understood` signal is stored. Two not-understood turns in a row force this mode; an unusable model reply is spoken as a fixed "could you say that again" and counts as not understood.
- **Call length cap (FR24 groundwork):** `AGENT_MAX_TURNS` (default 30) wraps up the call. This is a turn cap, not a time cap.
- **Agent gets the call date and time**, and its own wording of the timeline rule (be honest if clearly under the hard minimum, offer a later start, never say the week numbers). The classifier's wording (target date extraction) stays in the classifier.
- **Agent never repeats the same question twice in a row** (added after the first simulation showed it asking for carpet area four times when the scripted caller never answered).
- **Marathi / other languages:** not supported (open question). The agent is told to say so politely and take a message.

### Simulator: two caller modes (the literal script cannot answer questions)
- `--mode literal` (default, what the brief describes): the caller lines of each transcript in order, then one neutral line ("That's all I have for now, thank you") if the agent has not closed. Those lines were written for a human desk, so they often do not answer the agent's questions, which makes `ask_one_question` outcomes likely for reasons that are not the agent's fault.
- `--mode persona`: first line verbatim, then an LLM plays the caller using only the facts, attitude and requests in the original lines, so the agent's questions get answered. The persona model is `MODEL_CALLER` (defaults to the classifier model).
- Both write transcripts and the notes that would have gone to Telegram to `out/simulate-<mode>/`.
- Hard checks run on every agent turn of every conversation in both modes: AI disclosure first, no price leak, no stacked questions, no promised time/slot.
- T16 is simulated against a pre-seeded earlier lead and an unclaimed note (the system "already holds" Monday's enquiry); T17 is two calls from the same number (first drops after one line).
- Extra scenarios: a caller pressed on price four times (English), one in Hinglish, and a prompt-injection caller.

## Stage 3 - dashboard and voice adapter (2026-10-09)

### What was built
- **Dashboard** (`/dashboard`, `?days=7|30|90`): the nine spec panels (responsiveness, leads, designer response, funnel, outcomes, quality, escalations, cost, review), computed by a pure function (`src/lib/metrics.ts`) from the call log, with call-detail pages (`/dashboard/calls/<id>`: transcript, flags, code guards, extracted fields, handoff text, cost rows). Caller numbers are masked to the last four digits in tables. The Telegram note's "Call summary" link now resolves.
- **Demo data**: `npm run seed` writes ~200 synthetic calls into Supabase (`provider='demo'`, phones `99999...`); without Supabase, outside production, the dashboard renders the same data in memory with a yellow DEMO DATA banner. In production without Supabase it refuses to render (never silently fake numbers).
- **Cost panel**: monthly total (and projection), cost per call, cost per qualified lead, share of the average-project range, split into model usage / voice minutes / telephony. Costs come from per-call `costs` rows (classifier tokens, agent tokens, voice minutes, provider cost) at the configurable unit prices. Without `USD_TO_INR` the panel shows USD and INR side by side; I did not invent an exchange rate. Demo amounts use placeholder unit prices and are not real prices.
- **Voice adapter layer** (`src/lib/voice/`): `VoiceAdapter` interface (`verify`, `parse`), normalised events (`end_of_call_report`, `call_log`), a registry selected by `VOICE_PROVIDER`, and a **stub adapter** (shared-secret header, JSON contract). **No real provider adapter was written and no provider is hard-coded**; you pick after your spike, and the README says how to add one.
- **`POST /api/voice/webhook`**: authenticates through the adapter (fails closed), parses, then per event: classify -> merge repeat caller -> write call + costs -> send handoff. Idempotent on `(provider, providerCallId)` (also enforced by a unique index); a failed event returns 500 so the provider retries; one bad event does not stop a batch.
- **FR19**: telephony call-log rows (`call_log`) are recorded as calls with `source='front_desk'` and no classification (`classification_status='pending'`), unanswered calls as `dropped_or_missed`, and they appear in the responsiveness panel. They never create a lead or a note.
- **Text simulator** (`/simulator`): a browser chat that runs the real agent and classifier and shows the outcome and the note designers would receive. Nothing is saved or sent (in-memory store, capturing notifier), so rehearsals never pollute the dashboard.
- **Designer reply conventions** parsed from Telegram replies: first contact ("called"), consultation, fit verdict, project signed. These feed the designer-response and funnel panels. Migration `0002_dashboard.sql` adds `handoffs.first_contact_at`, `handoffs.fit_verdict`, `leads.consultation_at`, `leads.project_signed_at`.
- **Access control** (`src/proxy.ts`, Next 16's renamed middleware): HTTP Basic auth (any username, password `DASHBOARD_PASSWORD`) on `/dashboard`, `/simulator`, `/api/simulator`. Without the variable they return 503 in production and are open only on a developer machine. The dashboard contains transcripts and phone numbers; `DASHBOARD_PASSWORD` is the only protection, so use a long one or put it behind your SSO.

### Decisions and assumptions
- **Front-desk calls do not raise designer notes (OPEN).** They are logged and, if a transcript arrives, classified, but the designer handoff is skipped because the desk forwards them today. If you want notes for them too, change `handoff: answeredBy === "ai"` in `src/lib/voice/webhook.ts`.
- **"Time to answer"** is `answered_at - started_at` for every call; "answered within 5 min" is a share of all calls, so unanswered calls count against it. The pre-AI baseline (48% unanswered after 48 hours) cannot be computed from this log.
- **Designer response, consultations, projects and fit verdicts rely on designers replying in Telegram** with the phrases in the README. Free-text matching is fragile by nature (a reply that says "not called yet" would match "called"). If this proves noisy, replace it with buttons (inline keyboard) or a CRM feed. Until designers use the phrases those panels show dashes or zeros.
- **Funnel counts qualified leads, not qualified calls** (a repeat caller is one lead). A qualified call with no caller ID has no lead record and is not counted.
- **Demo rows can be deleted; real declined/escalated calls cannot.** The delete trigger now exempts `provider='demo'` so `npm run seed -- --reset` works.
- **The migration SQL was applied and tested in an in-memory Postgres (PGlite)**, not on Supabase: both files apply cleanly, real `not_a_fit` / `escalate` / `timeline_too_short` calls cannot be deleted, other outcomes and demo rows can, and the check constraints and foreign keys reject bad data. The `pgcrypto` extension line was stripped for that test only (Supabase provides it).
- `next dev` generated an `AGENTS.md` in the repo (Next 16 behaviour pointing agents at its bundled docs). It is harmless; delete it or set `agentRules: false` in `next.config.mjs`.
- No `vercel.json` cron is committed: Hobby plans reject sub-daily schedules at deploy time. See README step 5.

## Consultation booking (2026-10-10)
- **Decision.** The user wants the assistant to really book consultations. Answers given: the consultation is a **phone or video call**, there is **no calendar in use yet**, assignment **not decided**. I first recommended Cal.com, then built our own scheduler instead because (a) one shared resource and no existing calendar make fixed weekly hours enough, (b) Cal.com bookings normally need an attendee email, which phone callers rarely give, and Vaani's docs do not describe how Cal.com availability is checked, (c) our own booking keeps everything (note, dashboard, no double booking) in one place. Real calendar sync (Google Calendar free/busy) and per-designer assignment remain **OPEN**.
- **Rules (assumptions, all env-switchable):** one shared calendar; slots follow `OFFICE_DAYS`/`OFFICE_OPEN_HOUR`/`OFFICE_CLOSE_HOUR` (Mon-Sat, 10am-7pm IST); `BOOKING_SLOT_MINUTES=30`; at most `BOOKING_DAYS_AHEAD=14` days ahead; at least `BOOKING_MIN_NOTICE_HOURS=4` from now; `BOOKING_CAPACITY=1` consultation at a time (confirm how many designers can take a call at once); `BOOKING_MODE="phone or video call"`.
- **Parts:** `src/lib/booking.ts` (slot grid and atomic booking), `GET /api/booking/slots` and `POST /api/booking/book` (tools the Vaani assistant calls; secret in the URL `?key=`, answer within 10 s), table `bookings` and function `book_slot` (migration 0004; takes a per-slot advisory lock so two callers cannot take the same slot), handoff kind `booking_alert`.
- **Flow:** the assistant asks name and preferred weekdays -> Find consultation slots -> offers 2-3 exact labels -> caller chooses -> Book consultation. A booking immediately posts `CONSULTATION BOOKED ...` in the designers' group (so it is never lost if the call report never arrives). When the call report arrives, the booking made during that call is linked by time window (and by phone if given) to the call and lead, `leads.consultation_at` is set (feeds the funnel), the lead note gets a `Consultation booked: <slot> (phone or video call)` line, and calls with a booking are not flagged `agent_promise` for saying that time.
- **Safeguards:** the start must be an exact free slot on the grid (made-up, past, Sunday, too-soon or beyond-horizon times are refused); refusals carry the next three free slots; the assistant is told it may say a time only if a booking tool returned it, and that a booking exists only when the Book tool answered `ok: true`.
- **Not built:** cancel/reschedule (the designer handles that by phone), reminders to the customer (no SMS/email channel), a booking list on the dashboard, double-booking against a designer's personal calendar.
- Live checks: slots endpoint and booking endpoint work on the deployed app; booking the same slot twice is refused with alternatives; a made-up time is refused; the group message was delivered; test rows deleted. 249 tests pass. **Not yet tested:** Vaani actually calling these tools (depends on how Vaani's tool parameters are bound; the cURL templates in `vaani/booking-tools.local.txt` may need adjusting in its UI).
